= Data Index
:page-aliases:

Data Index is a read-only query service for Open Workflow 1.0.0 execution data.
It ingests workflow and task lifecycle events, normalizes them into workflow instances and task executions, and serves them through a GraphQL API.

It does not execute workflows, change workflow state, or store workflow definitions.

== What it runs as

Data Index ships as container images, one per backend:

[cols="2,1,3"]
|===
|Image |Role |Job

|`quay.io/kubesmarts/logic-data-index:<version>-postgresql`
|PostgreSQL storage
|GraphQL API on PostgreSQL. Also polls the raw event tables and normalizes them, unless Kafka ingestion is used.

|`quay.io/kubesmarts/logic-data-index:<version>-elasticsearch`
|Elasticsearch storage
|GraphQL API on Elasticsearch. Creates the indices and transforms that normalize raw events.

|`quay.io/kubesmarts/logic-data-index-ingestion:<version>-kafka`
|Kafka ingestion
|Consumes lifecycle CloudEvents from Kafka and writes them to PostgreSQL. No API.
|===

See xref:reference/images.adoc[Container images] for tags.

== Storage and ingestion

A setup is two choices, explained in xref:explanation/storage-and-ingestion.adoc[Storage and ingestion]:

* *Storage*: PostgreSQL or Elasticsearch, where workflow data lives and what the API reads.
* *Ingestion source*: raw events written into the storage's raw tables or indices, or CloudEvents consumed from Kafka.

Data Index owns the ingestion source, normalization and storage.
Shipping events to the ingestion source is outside Data Index: use a collector such as xref:integrations/vector.adoc[Vector], your own writer, or a Kafka producer in the app.

To deploy Data Index on Kubernetes together with a collector and your workflows, use the {logic-operator-url}[logic-operator^].
