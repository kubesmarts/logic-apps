= Storage and ingestion
:page-aliases:

A Data Index setup is described by two choices:

Storage:: Where workflow data lives and what the GraphQL API reads: *PostgreSQL* or *Elasticsearch*.
Ingestion source:: How lifecycle events enter Data Index: *raw events* written into the storage, or *Kafka*.

Data Index owns everything from the ingestion source onward: the raw event schema, normalization, storage and the API.
Producing events and shipping them to the ingestion source is not part of Data Index.

== Storage

[cols="1,3"]
|===
|Storage |What you get

|PostgreSQL
|One database for raw events and normalized data, ACID writes, JSONB filters.
The simplest setup to run.
Throughput is bounded by a single PostgreSQL writer; tens of thousands of workflows per day is comfortable.

|Elasticsearch
|Full-text search, aggregations and horizontal scaling.
In exchange, you run an Elasticsearch cluster, and normalization is eventually consistent.
|===

Details: xref:explanation/postgresql-storage.adoc[PostgreSQL storage], xref:explanation/elasticsearch-storage.adoc[Elasticsearch storage].

== Ingestion source

=== Raw events (default)

Each storage exposes raw event tables or indices as a public contract:

* PostgreSQL: `workflow_events_raw` and `task_events_raw`.
* Elasticsearch: `workflow-events-*` and `task-events-*`.

Anything that writes rows or documents in that shape feeds Data Index: a log collector, a batch job, or the application itself.
Data Index normalizes what lands there.
The columns and fields are listed in xref:reference/database-schema.adoc[Storage schema].

Getting events into the raw tables is up to you.
xref:integrations/vector.adoc[Vector] is a ready-made option that reads Quarkus Flow events from container logs.

=== Kafka

Data Index consumes lifecycle CloudEvents from a Kafka topic with a separate ingestion service, and writes them straight into the normalized tables.
There are no raw tables on this path.

Use it when the app can publish to Kafka and you would rather not depend on container logs, or need an encrypted, authenticated transport.
Kafka ingestion is supported with PostgreSQL storage only.

Details: xref:explanation/kafka-ingestion.adoc[Kafka ingestion].

== Supported setups

[cols="1,1,2"]
|===
|Storage |Ingestion source |Normalized by

|PostgreSQL
|Raw events
|Pollers in the `-postgresql` image

|Elasticsearch
|Raw events
|Elasticsearch transforms created by the `-elasticsearch` image

|PostgreSQL
|Kafka
|The Kafka ingestion service (`-postgresql` image polling turned off)
|===

Elasticsearch with Kafka is not supported.
With PostgreSQL, use one ingestion source at a time: when Kafka ingestion is on, turn raw-table polling off.

== Side by side

[cols="2,2,2,2"]
|===
| |PostgreSQL + raw events |Elasticsearch + raw events |PostgreSQL + Kafka

|Events enter through |`*_events_raw` tables |`*-events-*` indices |Kafka topic
|Normalization |JDBC polling in Data Index |Elasticsearch transforms |Kafka ingestion service
|Merge rules |SQL UPSERT |Painless scripts |SQL UPSERT (same code as polling)
|Failed events |`*_events_dlq` tables |— |`data-index-events-dlq` topic
|Search |Filters, JSONB |Full text, aggregations |Filters, JSONB
|Scaling |Vertical |Horizontal |Vertical (database)
|===

All setups serve the same GraphQL API.
xref:how-to/choose-a-setup.adoc[Choose a setup] turns this into a decision.
